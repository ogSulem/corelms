# CoreLMS

[![CI](https://github.com/ogSulem/corelms/actions/workflows/ci.yml/badge.svg)](https://github.com/ogSulem/corelms/actions/workflows/ci.yml)

CoreLMS — внутренняя LMS для обучения и контроля квалификации сотрудников.

Основные возможности:

- обучение по модулям/урокам
- материалы уроков в S3-совместимом хранилище
- тестирование (квизы), прогресс, XP
- единый редактор уроков, файлов, проверяемых AI-черновиков тестов и доступа; управление пользователями
- аудит безопасности (security audit log)

## Управление материалами без потери прогресса

Новый редактор: **Админ-центр → Модули → Редактировать**. Можно добавлять файлы без переимпорта, заменять и перемещать их, восстанавливать версии, архивировать материалы и обновлять существующий модуль из ZIP. Заработанное прохождение отделено от изучения новых материалов. Excel просматривается внутри LMS без внешнего Office iframe; для пересчёта формул скачивается оригинал.

Материал, конспект и файлы переключаются вкладками. Тесты, основной файл, предпросмотр и аудитория настраиваются в одном редакторе. «Продажи» разделены на Google Sheets с последней успешной копией и версионируемую S3-библиотеку. Отдельный `worker_media` автоматически готовит MP4 для видео и PDF для DOCX/PPTX, не меняя оригиналы.

Ручной текст защищён от ZIP-замены, у текста и файлов есть история версий. Дашборд ведёт к фактическому следующему шагу; обновления материалов отмечаются отдельно от полученного зачёта.

### Что именно происходит при повторном импорте модуля

1. Урок сопоставляется по **исходному пути внутри ZIP**. Если у старого импорта пути нет — только по однозначному совпадению названия и типа (урок/каталог). Неоднозначное совпадение не «угадывается»: создаётся новый урок, старый остаётся со своим прогрессом.
2. Названия, порядок, ручной текст, политика теста и архивное состояние существующего урока **не перезаписываются**. Текст обновляется, только если его не редактировали вручную; прежний сохраняется в истории версий.
3. Файлы сравниваются по контрольной сумме: изменённый получает новую версию (старую можно восстановить), отсутствующие в ZIP файлы не удаляются.
4. Зачёт по модулю (`module_completions`) привязан к пользователю и модулю, а не к редакции контента. Перед началом правки сервер фиксирует уже достигнутые результаты, поэтому после обновления ученик видит «результат сохранён, повторно проходить не нужно», а новый материал просто доступен для изучения.
5. Прогресс по урокам (`read`, результаты тестов) сохраняется, пока урок остаётся тем же. Если урок в ZIP переименован так, что совпадение потерялось, прогресс остаётся у старого урока — верните прежний путь или переименуйте материал в редакторе.

Ограничение: удаление модуля в интерфейсе удаляет его данные из БД; вернуть их можно только из резервной копии.

**Существующую установку нужно обновить до миграции `0026` с резервной копией. Перед первым пересозданием Redis перенесите его данные в новый persistent-том `redis_data`: теперь используются AOF и `noeviction`, а не вытеснение сессий и задач. Не запускайте `up` поверх старой установки без подготовки.**

→ [Возможности, ограничения, безопасное внедрение и проверки](docs/content-lifecycle.md)

Лицензия:

- репозиторий предоставляется для демонстрации/оценки
- для коммерческого использования нужен отдельный договор

## Состав репозитория

- **`frontend/`** — Next.js (UI + server routes `/api/*`)
- **`backend/`** — FastAPI (API + воркеры RQ + Alembic)
- **`nginx/`** — ingress для режима IP-only
- **`Caddyfile`** — ingress для режима домен+TLS (профиль `tls`)
- **`docker-compose.yml`** — единый способ запуска (локально/VPS)
- **`.env.example`** — минимальный шаблон запуска (без тюнинга)

## Как устроено (коротко)

### Один origin — это важно

Приложение рассчитано на **один публичный origin** (то, что вводят в браузере).

- `http://localhost:8080` и `http://127.0.0.1:8080` — **разные хосты**.
- Cookies `core_token/core_refresh` — host-only (если не задан `COOKIE_DOMAIN`).
- Поэтому “залогонился на localhost, открыл 127.0.0.1 — разлогинило” это нормально.

### Кириллический домен и вход

`edu.каркастайги.рф` можно писать и в `PUBLIC_APP_URL`, и в `CORS_ALLOW_ORIGINS`,
и в `COOKIE_DOMAIN`: браузер присылает punycode, а backend и frontend приводят
значения к ASCII перед сравнением и перед установкой куки.

`COOKIE_DOMAIN` нужен только для общего входа на нескольких поддоменах. Если
адрес, по которому открыт сайт, не совпадает с этим доменом (например, вход по
IP с телефона), кука ставится только для текущего хоста — вход работает, а не
теряется молча. Пустое значение всегда безопасно.

### Поток запросов

- Браузер открывает UI на `PUBLIC_APP_URL`.
- UI делает запросы по same-origin:
  - `/api/auth/*` — Next.js server routes (ставят/чистят httpOnly cookies)
  - `/api/backend/*` — прокси в backend (с учётом cookies)
- Backend не должен быть доступен напрямую из интернета: он доступен только внутри docker-сети.

### Фоновые процессы

| Контейнер | Что делает | Почему отдельно |
|---|---|---|
| `worker` | импорт и переобход ZIP-модулей, черновики тестов, уборка осиротевших объектов | два процесса RQ: долгий импорт не задерживает генерацию теста |
| `worker_media` | совместимые MP4/PDF и превью для видео и Office | нужен LibreOffice и до 1.5 ГБ памяти; тяжёлое кодирование не должно занимать общий воркер |

Раньше воркеров было четыре (`worker_import`, `worker_regen`, `worker_default`, `worker_media`) — три из них делали то же самое в разных очередях и вместе держали лишние ~250 МБ памяти. Очереди остались прежние (`corelms_import`, `corelms_regen`, `corelms_cleanup`, `corelms`), их список задаёт `RQ_WORKER_QUEUES`.

## Быстрый старт (локально)

1) Создай `.env`:

```bash
cp .env.example .env
```

2) Рекомендуемые значения для локалки:

- `NGINX_HTTP_PORT=8080`
- `PUBLIC_APP_URL=http://127.0.0.1:8080`
- `NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8080`
- `CORS_ALLOW_ORIGINS=http://127.0.0.1:8080`
- `COOKIE_SECURE=false`

3) Запусти:

```bash
docker compose up --build
```

Открыть:

- UI: `http://127.0.0.1:8080/`
- API: `http://127.0.0.1:8080/api/*`

### Отладочный профиль (прямой доступ к портам)

Если нужно опубликовать `backend:8000`, `frontend:3000`, `postgres:5432`, `redis:6379` только на `127.0.0.1`, используй:

```bash
docker compose --profile dev up -d --build
```

## Деплой на VPS (production)

Здесь описано два режима:

- **Режим 1: VPS IP-only (HTTP)** — nginx на произвольном порту (например `:8888`)
- **Режим 2: VPS домен + TLS (HTTPS)** — Caddy на `:80/:443` (профиль `tls`)

### Базовый принцип безопасности

- наружу публикуется только ingress (nginx или caddy)
- `backend`, `postgres`, `redis`, воркеры — только внутри docker-сети

### Шаги (общие)

1) На VPS создай `.env` из `.env.example`

2) Обязательно замени секреты:

- `JWT_SECRET_KEY`
- `BOOTSTRAP_ADMIN_PASSWORD`
- `POSTGRES_PASSWORD`
- `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY`

3) Проверь, что `ALLOW_PUBLIC_REGISTER=false`.

---

### Режим 1: VPS IP-only (HTTP через nginx)

Настройки:

- `NGINX_HTTP_PORT=8888` (или любой свободный)
- `PUBLIC_APP_URL=http://<VPS_IP>:8888`
- `NEXT_PUBLIC_API_BASE_URL=http://<VPS_IP>:8888`
- `CORS_ALLOW_ORIGINS=http://<VPS_IP>:8888`
- `COOKIE_SECURE=false`

Запуск (первая установка скачивает базовые образы; если Docker Hub отвечает ошибкой TLS — сначала
`bash deploy/pull-base-images.sh`, затем повторите):

```bash
docker compose up -d --build
```

Проверка:

- UI: `http://<VPS_IP>:8888/`
- API: `http://<VPS_IP>:8888/api/health/ready`

---

### Режим 2: VPS домен + TLS (HTTPS через Caddy)

Настройки:

- `CADDY_DOMAIN=lms.example.com`
- `CADDY_EMAIL=you@example.com`
- `PUBLIC_APP_URL=https://lms.example.com`
- `NEXT_PUBLIC_API_BASE_URL=https://lms.example.com`
- `CORS_ALLOW_ORIGINS=https://lms.example.com`
- `COOKIE_SECURE=true`

Запуск:

```bash
docker compose --profile tls up -d --build
```

## Обновление и миграции

### Что с вашим `.env` при обновлении

**Менять `.env` не нужно.** Новых обязательных переменных эта версия не добавляет: настройки AI, Google Sheets, S3, лимит загрузки и открытая регистрация теперь хранятся в таблице `app_settings` и задаются в интерфейсе. Переменные `OPENROUTER_*`, `SALES_LINKS_*`, `S3_*`, `CONTENT_UPLOAD_MAX_BYTES`, `ALLOW_PUBLIC_REGISTER` остаются как значения по умолчанию, к которым возвращает кнопка «Сбросить к серверу».

Что важно **не** менять:

- `JWT_SECRET_KEY` — от него по умолчанию выводится `SETTINGS_ENCRYPTION_KEY`. Смените — сохранённые токен AI и ключи S3 перестанут расшифровываться (интерфейс попросит ввести их заново). Если ключ шифрования задан отдельно, он тоже должен остаться прежним.
- `COOKIE_SECURE=true`, `CORS_ALLOW_ORIGINS=https://ваш-домен`, `PUBLIC_APP_URL=https://ваш-домен` — при смене домена меняются согласованно, иначе браузер перестанет отправлять cookie.
- `ALLOW_RUNTIME_S3_OVERRIDES` теперь ни на что не влияет, кроме чтения старых оверрайдов Redis `runtime:s3`. Значение можно оставить как есть, в том числе `false` в production: запись S3 из интерфейса работает всегда.
- `ALLOW_PUBLIC_REGISTER=true` в production по-прежнему запрещён проверкой при старте; включайте регистрацию в интерфейсе, в разделе «Платформа».

Копия `.env` сохраняется в каждой резервной копии (`env.backup`, права 600) — по ней всегда видно, какие значения были.

### Обновление с доменом и минимальным простоем

Домен, TLS и Caddy/nginx при обновлении не меняются: конфиг монтируется с диска, пересобирать его не нужно. Простой даёт только перезапуск контейнеров `backend` и `frontend` — это единицы секунд.

```bash
cd /opt/corelms

# 1) Копия (скрипт из этого репозитория)
./scripts/backup.sh --dir /srv/backups --keep 30

# 2) Код на опубликованную версию, без потери .env и backups/
git fetch origin && git checkout -f -B main origin/main

# 3) Собрать образы, пока старые контейнеры продолжают обслуживать запросы.
#    Нет доступа к Docker Hub? Соберите офлайн: bash deploy/update.sh
docker compose build backend frontend worker worker_media

# 4) Миграции отдельным шагом (0026 только добавляет таблицу, старый код с ней работает)
docker compose run --rm --no-deps --entrypoint alembic backend current
docker compose run --rm --no-deps --entrypoint alembic backend upgrade head

# 5) Заменить контейнеры по одному, не трогая postgres/redis
docker compose up -d --no-deps backend
docker compose up -d --no-deps frontend
docker compose up -d --no-deps worker worker_media

# 6) Проверка
curl -fsS https://ваш-домен/api/health/ready
docker compose ps
```

`--no-deps` обязателен: без него `up` может перезапустить PostgreSQL и Redis. `--build` в обычном `up` тоже не нужен — образы уже собраны на шаге 3, иначе сборка начнётся в момент остановки старого контейнера.

Если хочется совсем без обрыва: сделайте шаги 1–4 днём, а на шаге 5 перезапустите сервисы ночью или в обед — окно недоступности меньше десяти секунд, и его видит только тот, кто в этот момент отправляет форму.

Актуальная версия схемы: **`0026`**. Миграция `0024` добавляет таблицу `app_settings` для настроек, которые администратор меняет в интерфейсе: токен AI, доступ к Google Sheets, подключение к S3 и лимиты платформы. Секреты в ней шифруются (`enc:v1:`), в JSON-поле открытого текста нет. Точный head всегда виден в интерфейсе — приложение берёт его из Alembic, а не из константы.

Применяйте миграции **явным отдельным шагом**, а не «на глаз» при первом `up`:

```bash
# 0) Сначала резервная копия (обязательно)
mkdir -p backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/pre-0026.dump

# 1) Какая версия сейчас и какая ожидается
docker compose run --rm --no-deps --entrypoint alembic backend current
docker compose run --rm --no-deps --entrypoint alembic backend heads

# 2) Собрать API, frontend и все воркеры из одной версии кода
docker compose build backend frontend worker worker_media
#    или без сети: bash deploy/update.sh

# 3) Остановить писателей и применить схему
docker compose stop backend worker worker_media
docker compose run --rm --no-deps --entrypoint alembic backend upgrade head

# 4) Запустить всё
docker compose up -d backend worker worker_media frontend
```

Проверка после обновления:

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select version_num from alembic_version;"'
# ожидается 0026
curl -fsS http://127.0.0.1:8080/api/health/ready
```

Если API уже работает и обновлять контейнеры не нужно, достаточно:

```bash
docker compose exec backend alembic upgrade head
docker compose exec backend alembic current   # ожидается 0026 (head)
```

(У `docker compose run ... --entrypoint alembic` тот же результат для остановленного стека.)

Затем откройте **Админ-центр → Настройки**: блок «Сервер и схема данных» показывает текущую версию схемы и ожидаемый head. Если версии совпадают (например, `0026 / ожидается 0026`), миграция применена. Ожидаемый head вычисляется из каталога миграций, поэтому после следующего обновления сравнивать вручную не нужно.

Альтернатива: `AUTO_MIGRATE_ON_START=true` заставляет API применить `upgrade head` при старте (с advisory-lock). Для controlled-обновления это менее прозрачно: сначала всё равно сделайте backup и обновите API/воркеры согласованно. В `docker-compose.yml` у воркеров этот флаг принудительно `false`.

Откат: восстановите согласованный backup PostgreSQL вместе с прежней версией приложения. `alembic downgrade` не является безопасным production-откатом после появления новых данных.

Если миграция сообщает, что объект уже существует, не удаляйте данные: проверьте `alembic current`, журналы и восстановите backup/согласуйте схему вручную.

### Если Docker Hub недоступен (`TLS handshake timeout`)

Ошибка вида `failed to fetch anonymous token: ... TLS handshake timeout` означает, что сервер не достучался до `registry-1.docker.io`. Код и данные тут ни при чём. Три способа по порядку:

```bash
# 1) Повторить с паузами — чаще всего сеть провайдера отходит через минуту
bash deploy/pull-base-images.sh

# 2) Собрать вообще без внешней сети: новые образы кладутся поверх уже работающих
bash deploy/update.sh

# 3) Свой registry-зеркало (если доступ к Docker Hub закрыт постоянно)
#    /etc/docker/daemon.json:
#    { "registry-mirrors": ["https://mirror.gcr.io"] }
#    затем: systemctl restart docker && bash deploy/update.sh --build
```

`deploy/update.sh` собирает образы `corelms-*:next`, проверяет их и только потом подменяет `:latest`; тег `rollback-<дата>` остаётся для отката. Данные (`pg_data`, `redis_data`, `backend_data`, S3) не затрагиваются. Скрипт **не** запускает `docker compose up --build`, поэтому registry не нужен вообще.

> Важно: `docker image prune -af` удаляет промежуточные слои, на которых держится офлайн-сборка. После такой очистки первый `deploy/update.sh` может потребовать доступа к Docker Hub. Если чистите место — используйте `docker image prune -f` (без `-a`).

### Где хранятся файлы

Всё содержимое — в S3-совместимом хранилище: оригиналы, прошлые версии, браузерные копии, превью и файлы продаж. Локальный диск используется только как временный буфер при загрузке (`backend_data/upload-staging`) и очищается. Подробности, ключи объектов и правила очистки — в [docs/storage.md](docs/storage.md).

## Настройки в интерфейсе

**Админ-центр → Настройки** (`/admin/settings`):

- **AI для тестов** — токен OpenRouter (или совместимого API), модель, адрес API, проверка подключения. Кнопка **«Загрузить модели»** спрашивает у шлюза его собственный каталог (`/models`) и показывает, что реально доступно этому токену: бесплатные модели идут первыми, рядом с названием — пометка «бесплатно», в подсказке видно их количество. Поэтому устаревшее имя модели не нужно угадывать: список приходит с сервера, а не из зашитой в интерфейс подсказки. Токен хранится в БД в зашифрованном виде и имеет приоритет над `OPENROUTER_*` из `.env`; воркеры видят его без перезапуска. Кнопка «Сбросить к серверу» возвращает значения окружения.
- **Google Sheets для «Продаж»** — идентификатор таблицы, JSON сервисного аккаунта или API key, проверка чтения листов. Доступно супер-администратору. Файлы продаж в S3 работают и без таблицы.
- **Хранилище файлов (S3)** — bucket, адрес API, публичный адрес, регион, стиль адресации, ключи, кнопка «Проверить bucket» и «Сбросить к серверу». Значения хранятся в `app_settings` (ключи шифруются) и действуют сразу, без перезапуска и без флага `ALLOW_RUNTIME_S3_OVERRIDES`. Приоритет: сохранённые в интерфейсе значения → старый Redis-оверрайд `runtime:s3` (только для обновления) → `.env`.
- **Платформа** — максимальный размер загружаемого файла (от 1 МиБ до 20 ГиБ) и открытая регистрация. Значения применяются на следующем запросе: лимит загрузки в редакторе раздела, в «Продажах» и в публичной регистрации. По умолчанию — 5 ГиБ; большие файлы браузер отправляет частями по 8 МиБ и продолжает с места обрыва, поэтому видео на сотни мегабайт не приходится загружать заново.
- **Сервер и схема** — окружение, публичный URL, лимит файла, bucket, версия схемы, состояние фоновых воркеров.

Все изменения ведутся на `/admin/settings` (разделы «AI для тестов», «Продажи (Sheets)», «Хранилище файлов», «Платформа», «Сервер и схема»). Отдельного экрана «Диагностика» нет: состояние сервисов проверяется в блоке «Сервер и схема» кнопкой «Проверить» — она одним запросом к `/health/ready` подтверждает, что отвечают база, Redis и S3. Внешние сервисы (AI, Google Sheets) проверяются только по своей кнопке, поэтому страница не тормозит.

## Разделы админ-центра

Меню админ-центра состоит из четырёх пунктов, чтобы не дублировать одно и то же:

| Раздел | Адрес | Что делает |
|---|---|---|
| **Модули** | `/admin/modules` | Библиотека модулей, единый редактор, кнопка «Импорт нового ZIP» (`/admin/import`). |
| **Пользователи** | `/admin/users` | Список людей с поиском и фильтром по роли, карточка с результатами, смена роли (суперадмин), сброс пароля, удаление, теги доступа, создание пользователя с временным паролем. |
| **Результаты** | `/admin/analytics` | Прогресс по модулям и по людям: начали, завершили, средний процент, попытки тестов, сдача, средний балл, активность. |
| **Настройки** | `/admin/settings` | AI, Google Sheets, S3, лимиты платформы, «Сервер и схема» с проверкой сервисов. |

Импорт (`/admin/import`) — подчинённый экран раздела «Модули»: отдельного пункта в меню нет, кнопка «Импорт нового ZIP» ведёт туда из библиотеки. Он загружает архив напрямую в хранилище (до 64 МБ одним запросом, больше — частями) и показывает очередь фонового разбора.

Ключ шифрования: `SETTINGS_ENCRYPTION_KEY`, иначе используется `JWT_SECRET_KEY`. Если ключ изменился, сохранённые токены перестают читаться — интерфейс попросит ввести их заново.

### Как генерируются тесты

1. В редакторе модуля откройте вкладку «Тесты» и выберите урок.
2. AI получает текст урока, документ (PDF/DOCX/PPTX) или вставленный фрагмент (до 12 000 символов) и возвращает **черновик** вопросов с вариантами и пояснениями. Сканы без текстового слоя и видео автоматически не распознаются.
3. Черновик не публикуется сам: проверьте вопросы и сохраните тест кнопкой «Сохранить тест».
4. «Подготовить тесты для всех уроков» создаёт черновики пачкой (до 50 уроков), только для уроков без вопросов или для всех.
5. Без токена AI тесты создаются вручную; обучение, файлы и прогресс от AI не зависят.

Для фоновой генерации должен работать контейнер `worker` (очередь `corelms_regen`).

## Резервные копии и восстановление

Данные лежат в двух persistent-томах Docker: `pg_data` (PostgreSQL) и `backend_data` (локальные файлы; основные материалы — в S3). Том переживает перезапуск и обновление кода, но **том — это не резервная копия**: ошибка, неудачная миграция или удаление контента в интерфейсе попадают и в том. Автоматических копий до этой версии не было — ниже рабочая процедура.

### Разовая копия

```bash
cd /opt/corelms
./scripts/backup.sh                 # в ./backups, хранит 14 последних копий
./scripts/backup.sh --keep 30       # хранить 30
./scripts/backup.sh --dir /srv/backups --redis
```

Скрипт делает `pg_dump -Fc`, сразу проверяет дамп через `pg_restore --list` (битая копия удаляется и скрипт падает), сохраняет том `backend_data`, копию `.env` (в ней пароль БД и ключ шифрования настроек) и `MANIFEST.txt` с версией схемы и контрольными суммами. Ничего не удаляет и не останавливает.

### Регулярная копия (cron)

```bash
sudo crontab -e
# каждый день в 03:30, лог рядом с копиями
30 3 * * * cd /opt/corelms && ./scripts/backup.sh --dir /srv/backups --keep 30 >> /var/log/corelms-backup.log 2>&1
```

Храните копии **вне сервера** (`rsync`/`rclone` в отдельный бакет). Не включайте Lifecycle-удаление на бакете с материалами.

### Проверка, что копия действительно восстанавливается

Раз в месяц — на отдельной БД, не на рабочей:

```bash
docker compose exec -T postgres sh -c 'createdb -U sdlp restore_check'
docker compose exec -T postgres pg_restore -U sdlp -d restore_check --no-owner < backups/<копия>/db.dump
docker compose exec -T postgres sh -c 'psql -U sdlp -d restore_check -tAc "select count(*) from users; select count(*) from module_completions;"'
docker compose exec -T postgres sh -c 'dropdb -U sdlp restore_check'
```

Если вторая цифра (зачёты) не ноль и растёт — прогресс учеников на месте.

### Восстановление

```bash
cd /opt/corelms
./scripts/restore.sh backups/corelms-2026-10-27_03-30-00 --yes
```

Без `--yes` скрипт ничего не делает. Дальше он сам снимает предупредительную копию текущего состояния, останавливает API и воркеров, заливает дамп (`pg_restore --clean --if-exists --no-owner`), поднимает сервисы и печатает версию схемы. Файлы S3 не трогаются. Если менялись `JWT_SECRET_KEY` или `SETTINGS_ENCRYPTION_KEY`, верните прежние значения: без них сохранённые токен AI и ключи S3 не расшифруются (интерфейс попросит ввести их заново).

Откат после неудачной миграции — это восстановление копии вместе с прежней версией приложения, а не `alembic downgrade`.

## Перенос данных (локально -> VPS)

Локально:

## Troubleshooting

### Сервер разошёлся с `origin/main` (правили файлы прямо на сервере)

Типичная картина: `git status` показывает «diverged», в дереве мусор вида `[backend]`, `CACHED`, `exporting`, `writing` (следы `git add *`), а `git pull` падает с `CONFLICT` в чужих файлах.

Порядок действий — **не** мержить вслепую и **не** делать `git add *`:

```bash
# 1) Сначала копия. Без неё дальше не идти.
cd /opt/corelms && ./scripts/backup.sh --dir /srv/backups --no-files

# 2) Сохраните свои локальные правки и коммиты в сторону
mkdir -p /root/corelms-server && cp -a Caddyfile modules_tree.md /root/corelms-server/ 2>/dev/null || true
git log --oneline origin/main..HEAD > /root/corelms-server/local-commits.txt
git branch server-local-$(date +%F)

# 3) Если merge уже начат и он в конфликтах — отмените его
git merge --abort 2>/dev/null || true

# 4) Встаньте ровно на опубликованную версию и удалите мусор
git fetch origin
git checkout -f -B main origin/main
git clean -fd            # уберёт [backend], CACHED…; .env и backups/ не тронет
```

`git clean -fdx` использовать нельзя: флаг `-x` удалит `.env` и каталог копий. Возвращать локальные правки — по одному файлу через `diff`, а не целиком.

`git add *` в корне — источник мусорных коммитов: `*` не раскрывает скрытые файлы, зато захватывает случайные. Используйте `git add -p` или явные имена. Пароль в `git push` GitHub больше не принимает: нужен токен или SSH-ключ, а пушить удобнее из GitHub, а не с сервера.

### Частый случай: “после перезагрузки выкинуло”

Проверь:

- не поменял ли ты `localhost` на `127.0.0.1` (или наоборот)
- при HTTP должен быть `COOKIE_SECURE=false`
- `docker compose down -v` удаляет persistent-тома, включая БД и Redis; не используйте эту команду для обычного обновления. Обычный `down` не удаляет тома. Без авторитетной Redis-сессии доступ и refresh не принимаются

### Очереди не исполняются

- открой админку, вкладка diagnostics/jobs: `WORKERS: 0` значит воркеры не поднялись
- проверь контейнеры `worker`, `worker_media`
- проверь `REDIS_URL`

### CORS ошибки

- `CORS_ALLOW_ORIGINS` должен точно совпадать с `PUBLIC_APP_URL` (origin в браузере)

## Advanced: опциональные переменные окружения

`.env.example` специально минимальный. Ниже — опциональные настройки из `backend/app/core/config.py`.

### OpenRouter (если нужен AI)

- `OPENROUTER_ENABLED=true`
- `OPENROUTER_API_KEY=...`

Опционально:

- `OPENROUTER_BASE_URL`
- `OPENROUTER_MODEL`
- `OPENROUTER_TIMEOUT_CONNECT`
- `OPENROUTER_TIMEOUT_READ`
- `OPENROUTER_TIMEOUT_WRITE`
- `OPENROUTER_TEMPERATURE`
- `OPENROUTER_HTTP_REFERER`
- `OPENROUTER_APP_TITLE`
- `LLM_PROVIDER_ORDER`

### LLM debug (диагностика генерации квизов)

По умолчанию debug выключен.

- `LLM_DEBUG_SAVE=true` — сохранять диагностические срезы в meta RQ job (видно в админке)
- `LLM_DEBUG_LOG=true` — писать эти срезы в логи worker
- `LLM_DEBUG_MAX_CHARS=2000` — лимит на размер сниппетов

Важно: при включении debug может содержать фрагменты текста уроков и вывода модели.

### S3 тюнинг (таймауты, presign TTL и т.д.)

- `S3_REGION_NAME`
- `S3_ADDRESSING_STYLE`
- `S3_PRESIGN_DOWNLOAD_EXPIRES_SECONDS`
- `S3_PRESIGN_UPLOAD_EXPIRES_SECONDS`
- `S3_PRESIGN_MULTIPART_PART_EXPIRES_SECONDS`
- `S3_CONNECT_TIMEOUT_SECONDS`
- `S3_READ_TIMEOUT_SECONDS`
- `S3_MAX_ATTEMPTS`
- `S3_MAX_POOL_CONNECTIONS`

### Хранение исходников и версий

После `0021`/`0022` физическая TTL-очистка файлов/ZIP работает только как диагностика: данные не удаляются по неполному снимку ссылок. Архивирование выполняется в редакторе. Не включайте внешнюю S3 Lifecycle expiration для материалов и их версий; запланируйте объём хранения и отдельную политику retention.

Операционные настройки диагностики и незавершённых multipart-загрузок:

- `UPLOADS_ADMIN_TTL_HOURS`
- `UPLOADS_ADMIN_CLEANUP_INTERVAL_MINUTES`
- `UPLOADS_ADMIN_MULTIPART_TTL_HOURS`
- `UPLOADS_ADMIN_MULTIPART_MAX_ABORT`
