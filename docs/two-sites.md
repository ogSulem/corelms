# Два сайта на одном сервере: кто держит порт 80/443 и что делать

Короткий ответ: **на одном порту может работать только один сервер.** У CoreLMS два взаимозаменяемых
«входа» — обычный `nginx` и `Caddy` с HTTPS. Если порт 443 уже занят веб-сервером второго сайта (или
системным nginx на сервере), то наш стек остаётся на внутреннем порту, а HTTPS делает чужой сервер.

---

## 1. Как это устроено

```
                   ┌─► frontend:3000  интерфейс, /api/auth/*, /api/backend/*
браузер ─► :443 ───┤
                   └─► backend:8000   /api/upload/*, /health/*

                   ┌─► frontend:3000
браузер ─► :8888 ──┤        (это наш nginx)
                   └─► backend:8000
```

* **наш nginx** (`corelms-nginx-1`) — обязателен, стартует всегда. Отдаёт интерфейс, проксирует
  `/api/*`, `/api/upload/*` (большие файлы мимо Next.js) и `/api/health/*` в API, ограничивает частоту.
  Слушает порт из `.env` (`NGINX_HTTP_PORT`, по умолчанию `80`, на сервере с вторым сайтом — `8888`).
* **Caddy** (`corelms-caddy-1`) — необязательный вход с HTTPS, включается профилем `tls`
  (`docker compose --profile tls up -d`). У него **свои** правила маршрутизации: он проксирует прямо в
  `frontend`/`backend`, а не через наш nginx. Сам получает сертификат Let's Encrypt.
* Поэтому два варианта: либо HTTPS держит **Caddy внутри стека**, либо **внешний сервер** (второй сайт,
  системный nginx, Cloudflare и т. п.), который проксирует домен CoreLMS на `NGINX_HTTP_PORT`.
* Одновременно `nginx` и `caddy` на одном порту не поднимутся: кто-то один должен уступить.

## 2. Что у вас сейчас (по одной команде в строку)

```
cd /opt/corelms
```

```
ss -lntp | grep -E ':(80|443)\b'
```

```
docker ps --format '{{.Names}}\t{{.Ports}}\t{{.Image}}'
```

```
grep -E '^(NGINX_HTTP_PORT|CADDY_DOMAIN|COMPOSE_PROFILES|PUBLIC_APP_URL)=' .env
```

### Как читать результат

| Что видно | Что это значит | Что делать |
| --- | --- | --- |
| на `:443` держит порт **не** контейнер стека (`docker-proxy` для `corelms-caddy` нет), а сайт по `https://` открывается | HTTPS терминирует внешний веб-сервер (второй сайт или системный nginx) | ничего не менять. Наш nginx слушает `NGINX_HTTP_PORT` (обычно `8888`), внешний сервер проксирует домен CoreLMS на него |
| на `:443` стоит `corelms-caddy-1` | HTTPS внутри стека, профиль `tls` включён | nginx должен быть на другом порту (`NGINX_HTTP_PORT=8888`), 80 и 443 — у Caddy |
| ни `:80`, ни `:443` никто не слушает, по `https://` сайт не открывается | HTTPS нет | включить Caddy: `docker compose --profile tls up -d` (и освободить 80/443) |
| на `:80` стоит **системный** nginx (не Docker) | на сервере свой веб-сервер, общий для сайтов | оставить как есть; он проксирует на `NGINX_HTTP_PORT` нашего стека |

Признак, что цепочка собрана правильно: `curl -fsS https://домен/api/health/ready` отвечает
`{"status":"ready"}` — значит внешний сервер, вход CoreLMS и API работают в связке.

## 3. Частые ошибки

1. **Включить профиль `tls` поверх чужого веб-сервера.** Два процесса не могут слушать 443: Caddy либо
   упадёт с «address already in use», либо займёт порт вместо второго сайта.
2. **Поставить нашему nginx `NGINX_HTTP_PORT=80`, когда 80 уже занят.** Контейнер не поднимется, сайт
   CoreLMS будет отдавать 502 со стороны внешнего сервера.
3. **Проксировать домен на `http://127.0.0.1:3000`** (порт интерфейса) в обход входа. Тогда перестают
   работать `/api/upload/*` (большие файлы), `/api/health/*` и ограничения частоты. Правильно — на наш
   nginx: `http://127.0.0.1:8888` (или другой порт из `NGINX_HTTP_PORT`).
4. **Менять порт у работающего стека, не поправив внешний сервер.** Порядок: сначала `.env` и внешний
   конфиг, потом `docker compose up -d --no-deps nginx`.

## 4. Реальный IP клиента (лимиты входа и журнал безопасности)

Если запрос идёт через внешний сервер, он должен передавать адрес клиента заголовком
`X-Forwarded-For`. Наш nginx доверяет таким заголовкам **только от внутренних сетей** (Docker) и
вычисляет адрес сам — подделать его снаружи нельзя.

Проверить, что реальный адрес доходит:

```
docker compose logs --tail=400 backend | grep -o '"ip": "[^"]*"' | sort | uniq -c | sort -rn | head
```

Если на все запросы один и тот же внутренний адрес (`172.x.x.x`, `10.x.x.x`), внешний сервер не
передаёт `X-Forwarded-For`, и лимит входа по адресу считается общим на всех. Лечится строкой в конфиге
внешнего nginx:

```
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

Для журнала запросов нужен `LOG_LEVEL=INFO` в `.env`: по умолчанию `WARNING`, и `docker compose logs
backend` почти пуст — об этом предупреждает самопроверка после обновления.

## 5. Что проверять после любого изменения на входе

```
curl -fsS https://домен/api/health/ready
```

```
curl -fsSI https://домен/login | head -5
```

```
curl -fsS https://домен/api/health/version
```

Первое — связка «вход → API» жива. Второе — интерфейс отдаётся, заголовки безопасности на месте.
Третье — поднята та версия кода, которую вы обновляли.

## 6. Caddy и nginx в обновлении

`deploy/update.sh` сам перечитывает конфигурацию входа: для nginx — `nginx -t` и `nginx -s reload`,
для Caddy (если контейнер запущен) — `caddy validate` и `caddy reload`. Оба конфига монтируются с диска
и без этого шага продолжали бы работать по-старому. При ошибке в конфиге остаётся работать прежняя
версия, сайт не падает.
