# Долгая работа без обслуживания: что копится и что ограничено

Платформа рассчитана на VPS, который месяцами работает без администратора. Ниже — что уже ограничено
автоматически, что растёт линейно (и насколько это безопасно), и что нужно сделать руками один раз.

## 1. Ограничено автоматически

| Что | Предел | Где задано |
| --- | --- | --- |
| Логи контейнеров | 10 МБ × 3 файла на каждый сервис | `docker-compose.yml`, `logging` у всех 8 служб |
| Журнал ошибок для админки | 2 МБ + один предыдущий файл | `app/services/error_log.py` |
| Ключи Redis (сессии, блокировки, счётчики) | у каждого есть TTL; задаётся вместе со значением | `set(..., ex=)` и `expire(nx=True)` |
| Неудачные задачи очереди | удаляются по `failure_ttl` (от часа до недели) | параметры `enqueue(...)` |
| Резервные копии | `--keep 30` (30 последних каталогов) | `scripts/backup.sh` |
| Образы отката `*:rollback-<дата>` | 3 последних набора из четырёх образов | `deploy/update.sh` |
| Кэш сборки Docker (BuildKit) | всё старше 7 дней удаляется при обновлении | `deploy/update.sh` |
| Промежуточные загрузки в S3 | отчёт по кандидатам каждые 15 минут | `app/services/maintenance_schedule.py` |
| Просроченные ссылки сброса пароля | старше 30 дней удаляются каждые 15 минут | `app/services/password_reset.py`, `maintenance_schedule.local_tasks` |
| Брошенные сессии докачки (части файлов на диске) | старше 24 часов удаляются каждые 15 минут | `app/services/chunked_uploads.py` |

## 2. Что растёт линейно

Цифры с рабочей установки (93 пользователя, полгода): `learning_events` — 21 391 строка,
`quiz_attempts` — 1 581. Это примерно 4 тысячи событий в месяц, то есть:

| Горизонт | `learning_events` | Размер в базе |
| --- | --- | --- |
| 1 год | ~50 тыс. строк | ~10 МБ |
| 3 года | ~150 тыс. строк | ~30 МБ |
| 10 лет | ~500 тыс. строк | ~100 МБ |

Для PostgreSQL это небольшой объём: индексы под ленту и историю добавлены (миграция `0029`), запросы
идут по `(user_id, created_at)`. Точно так же ведут себя `quiz_attempts`, `lesson_revisions`,
`security_audit_events` — рост есть, но он в разы меньше, чем у медиафайлов.

**Вывод: чистить базу от истории не нужно.** Если когда-нибудь захочется уменьшить архив, это делается
осознанно и вручную (ниже), а не автоматикой: история обучения — это данные учеников.

## 3. Что нужно сделать один раз

### Резервные копии по расписанию

Копии не делаются сами: `scripts/backup.sh` нужно запускать по cron.

```
crontab -e
```

и одна строка:

```
0 3 * * * cd /opt/corelms && ./scripts/backup.sh --dir /srv/backups --keep 30 >> /var/log/corelms-backup.log 2>&1
```

Проверка, что работает:

```
ls -la /srv/backups | tail -5
```

Копия без проверки восстановления — это надежда, а не копия. Раз в полгода стоит развернуть одну копию
на тестовой машине (`./scripts/restore.sh /srv/backups/corelms-… --yes`) или хотя бы посмотреть
`MANIFEST.txt` и убедиться, что `db.dump` и `files.tar.gz` не пустые.

### Обновления кода

```
cd /opt/corelms
```

```
git fetch origin && git checkout -f -B main origin/main
```

```
bash deploy/update.sh
```

Скрипт сам убирает старые образы отката и кэш сборки, поэтому диск не растёт от частых обновлений.

## 4. Проверка раз в месяц (три команды, минута)

```
df -h / && docker system df
```

```
docker compose exec -T backend python scripts/selfcheck.py | tail -40
```

```
curl -fsS https://домен/api/health/ready
```

Нормы: свободного места больше 20%, `docker system df` не показывает десятков гигабайт в
`RECLAIMABLE`, в самопроверке нет строк «медленно» на пользовательских страницах, `/api/health/ready`
отвечает `{"status":"ready"}`.

## 5. Если место всё-таки кончилось

От большего к меньшему — сначала смотрим, что занимает:

```
docker system df -v | head -30
```

```
du -sh /srv/backups /var/lib/docker /tmp 2>/dev/null
```

Безопасно освобождает:

```
docker image prune -f
```

```
docker builder prune -f --filter until=168h
```

Не удаляйте тома `pg_data`, `redis_data`, `backend_data` — это данные платформы. `docker compose down -v`
удаляет их безвозвратно.

## 6. Если когда-нибудь понадобится сократить историю (осознанно)

Сначала посмотрите, сколько это строк:

```
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select count(*) from learning_events where created_at < now() - interval '"'"'3 years'"'"';"'
```

Удаление старше трёх лет (история учеников за последние три года остаётся) — только после резервной
копии:

```
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "delete from learning_events where created_at < now() - interval '"'"'3 years'"'"';"'
```

Аналогично для `security_audit_events`. После удаления разово:

```
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "vacuum (analyze) learning_events;"'
```

## 7. Что не копится, хотя могло бы

- **Docker-логи** — ограничены на уровне compose, а не «пока не кончится диск».
- **Кэш сборки** — чистится при каждом обновлении, кэш старше недели удаляется.
- **Образы отката** — держатся три последних набора, остальные удаляются автоматически.
- **Ключи Redis** — заводятся только с TTL; отдельный тест `tests/test_redis_key_hygiene.py` следит,
  чтобы никто не добавил `set` без срока жизни.
- **Временные загрузки** — по ним есть автоматический отчёт с кандидатами на удаление; обучающие файлы
  и исходные архивы защищены списком ссылок из базы и очереди импорта.
- **Неудачные задачи очереди** — истекают по `failure_ttl`, реестр чистит сам RQ.
- **Брошенные сессии докачки и просроченные ссылки сброса пароля** — убираются по расписанию
  (`sweep_local_junk` в `maintenance_schedule`), а не только «когда пользователь начнёт загрузку»:
  на установке без активности они раньше оставались навсегда.
