# Обновление production

Инструкция для сервера, где платформа уже работает (каталог `/opt/corelms`, Docker Compose v2).
Первую установку с нуля описывает README, здесь — только обновление работающей платформы.

Данные не теряются: копия делается до любых изменений, тома `pg_data`, `backend_data`, `redis_data`
и файлы в S3 обновление не затрагивает.

---

## Короткий путь (обычное обновление)

По одной команде в строку, по порядку. Копировать целиком блок нельзя — выполняйте построчно.

```
cd /opt/corelms
```

```
./scripts/backup.sh --dir /srv/backups --keep 30
```

```
git fetch origin
```

```
git checkout -f -B main origin/main
```

```
bash deploy/update.sh
```

Готово. Скрипт сам: соберёт образы (без Docker Hub), применит миграции, переключит контейнеры,
перечитает конфигурацию nginx, дождётся готовности API и запустит самопроверку.

---

## Что именно делает `deploy/update.sh`

1. проверяет `docker-compose.yml` настоящим парсером compose (дубликат ключа валит `up` уже после сборки);
2. тегирует текущие образы как `*:rollback-<дата>` — это точка возврата;
3. собирает новые образы из исходников поверх уже имеющихся (Docker Hub не нужен);
4. удаляет контейнеры воркеров старой схемы, если они остались;
5. **применяет миграции базой новым образом, пока старые контейнеры ещё работают** — новый код не
   успевает поработать на старой схеме;
6. поднимает `backend`, `worker`, `worker_media`, `frontend` без обращения к registry;
7. перечитывает `nginx/default.conf` (сначала `nginx -t`; при ошибке остаётся работать прежний конфиг);
8. ждёт готовности API (`GET /health/ready` внутри контейнера) не дольше 2 минут;
9. запускает `scripts/selfcheck.py` (0 — хорошо, 2 — предупреждения настройки, 1 — ошибки эндпоинтов);
10. печатает команды отката и удаляет только промежуточные слои без тегов.

Отдельные части: `bash deploy/update.sh backend` — только API и воркеры; `frontend` — только интерфейс;
`--build` — сначала попробовать обычную сборку, если доступ к Docker Hub есть.

## Если обновляетесь впервые после долгого перерыва

Сначала посмотрите, где вы сейчас:

```
docker compose exec -T backend alembic current
```

```
docker compose exec -T backend alembic heads
```

- **Версии совпали** — обновлять схему нечего, но код всё равно обновите: `bash deploy/update.sh`.
- **Текущая версия ниже**, но не ниже `0026` — обычный путь выше. Миграции `0021`–`0029` только
  добавляют объекты (колонки, таблицы, индексы) и доливают значения, поэтому применяются подряд
  безопасно.
- **Версия ниже `0026`** (или `alembic current` отвечает ошибкой) — сначала выполните подготовку из
  README, раздел «Обновление и миграции»: перенос данных Redis в том `redis_data` (там теперь AOF и
  `noeviction`). Без этого после первого пересоздания контейнера Redis пропадут активные сессии — люди
  залогинятся заново, но очереди задач, стоявшие в памяти, потеряются.

Место на диске проверьте заранее — обновление пишет новые образы, а копия базы и построение индексов
тоже занимают место:

```
df -h /
```

```
docker system df
```

Ориентир: свободных 5–10 ГБ достаточно для обычного обновления; если меньше — удалите старые образы
`docker image prune -f` (не `-a`: теги отката `*:rollback-<дата>` останутся).

## Проверка после обновления

```
curl -fsS https://ВАШ-ДОМЕН/api/health/ready
```

Ожидается `{"status":"ready"}`. Если 503 — в ответе написано, что не готово (`db`, `redis` или `s3`).

```
curl -fsS https://ВАШ-ДОМЕН/api/health/version
```

Ожидается `{"version":"<хеш коммита>-<дата>"}` — этот хеш печатает в начале `deploy/update.sh`.
Если там старая дата, контейнер не пересобрался: смотрите `docker compose ps` и `docker compose logs --tail=80 backend`.

```
docker compose ps
```

Все сервисы `running` (или `healthy`), ничего не в `restarting`.

```
docker compose exec -T backend alembic current
```

Версия схемы. Ожидаемый head показывает `docker compose exec -T backend alembic heads`;
он же виден в **Админ-центре → Настройки → «Сервер и схема данных»** — там сравниваются
«текущая / ожидаемая» и не нужно ничего помнить наизусть.

Проверка руками (одна минута): вход в систему, открытие модуля, один вопрос теста, загрузка файла в
редакторе модуля. Этого достаточно, чтобы увидеть, что БД, S3, Redis и интерфейс живы.

## Если что-то пошло не так

### Вернуться к прежнему коду (данные не трогаются)

`<дата>` — тот самый суффикс `rollback-<дата>`, который напечатал `deploy/update.sh`.

```
docker tag corelms-backend:rollback-<дата> corelms-backend:latest
```

```
docker tag corelms-frontend:rollback-<дата> corelms-frontend:latest
```

```
docker compose up -d --no-build --no-deps backend worker worker_media frontend
```

Схема БД при этом остаётся новой. Миграции в проекте аддитивные (новая колонка, доливка данных,
индекс), поэтому прежний код с новой схемой работает. `alembic downgrade` для отката не используйте:
после появления новых данных это разрушительная операция.

### Восстановить базу из копии

Только если данные испорчены, а не просто «новая версия не понравилась».

```
./scripts/restore.sh /srv/backups/corelms-<дата> --yes
```

Скрипт сам снимает страховочную копию текущего состояния, останавливает API и воркеры, заливает дамп
и поднимает сервисы. Файлы S3 он не трогает.

## Чего не делать при обновлении

- `docker compose down -v` — удаляет тома с базой и Redis. Обычный `down` тома не удаляет.
- `docker compose up -d --build` — сборка начинается в момент остановки старого контейнера, и если
  Docker Hub недоступен, сайт останется лежать без работающей сборки. Для этого есть `deploy/update.sh`.
- Менять `JWT_SECRET_KEY` — от него выводится ключ шифрования настроек; после смены сохранённые токен
  AI и ключи S3 перестанут расшифровываться. Аналогично `SETTINGS_ENCRYPTION_KEY`, если задан отдельно.
- Менять `COOKIE_SECURE`, `CORS_ALLOW_ORIGINS`, `PUBLIC_APP_URL` поодиночке: при смене домена они
  меняются согласованно, иначе браузер перестаёт отправлять cookie и человек «входит и сразу вылетает».

## `.env` при обновлении

Новых **обязательных** переменных нет: настройки AI, Google Sheets, S3, лимит загрузки и открытая
регистрация хранятся в таблице `app_settings` и меняются в интерфейсе, `.env` остаётся значениями по
умолчанию, к которым возвращает кнопка «Сбросить к серверу».

Необязательные, добавленные для устойчивости (можно не задавать, есть значения по умолчанию):

- `DB_CONNECT_TIMEOUT_SECONDS=10` — сколько ждать соединения с PostgreSQL. Без него при недоступной
  базе запрос висит до системного таймаута (до двух минут), а пул соединений забивается.
- `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_POOL_TIMEOUT_SECONDS`, `DB_POOL_RECYCLE_SECONDS` — размеры пула.

Копия `.env` лежит в каждой резервной копии (`env.backup`, права 600): по ней всегда видно, какие
значения были.

## Что изменилось в этой версии и требует внимания при обновлении

1. **Маршруты `/api/health/*`.** `curl .../api/health/ready` раньше возвращал 404: путь никто не
   обслуживал, и проверка после обновления выглядела как поломка. Теперь nginx проксирует четыре
   точных адреса (`/api/health`, `/api/health/live`, `/api/health/ready`, `/api/health/version`) в API.
   Конфигурация монтируется с диска, поэтому её нужно перечитать — `deploy/update.sh` делает это сам.
   Вручную: `docker compose exec nginx nginx -t` затем `docker compose exec nginx nginx -s reload`.
2. **Адрес клиента.** nginx теперь определяет его сам (`realip`, доверяет только внутренним сетям), а
   не берёт из присланных заголовков. Для вас это значит корректные IP в журнале безопасности и
   работающий лимит входа по адресу. За Caddy (профиль `tls`) реальный адрес сохраняется.
3. **Индексы журнала обучения (`0029`).** Строятся `CONCURRENTLY`, запись в таблицы не блокируется.
   На большой истории это может занять от секунд до пары минут — обновление в это время ждёт.
   Если построение оборвалось (кончилось место, убили контейнер), повторный запуск `bash deploy/update.sh`
   увидит невалидный индекс и пересоздаст его.
4. **Пределы запросов.** Платный вызов провайдера AI из настроек ограничен 10 вызовами в минуту,
   повтор импорта — 30, старт и финиш большой загрузки — 300/240 в минуту. Обычная работа это не
   затрагивает: сто файлов, брошенных в окно разом, проходят.
5. **Модели схемы приведены к миграциям.** Тест `tests/test_schema_drift.py` теперь роняет сборку при
   любом расхождении модели и миграций — «забыли миграцию» больше не доедет до сервера.

Ничего из этого не требует ручной правки базы: всё делает `bash deploy/update.sh`.

## Сколько это занимает и сколько длится простой

- сборка образов — самая долгая часть (обычно 2–6 минут), сайт в это время работает на прежней версии;
- миграции — секунды, на большой истории обучения `0029` может занять до пары минут;
- переключение контейнеров — единицы секунд на сервис;
- `nginx -s reload` — без простоя (старые соединения доигрываются).

Итого недоступность — от нескольких секунд до пары минут, и только для тех, кто в этот момент отправляет
форму. Можно делать днём: ночью окно не требуется.

## Проверено и не проверено

Проверено в этом репозитории: синтаксис `deploy/update.sh` (`bash -n`), валидность `docker-compose.yml`
(`deploy/check-compose.py` + `docker compose config` в CI), синтаксис `nginx/default.conf` парсером nginx
(`crossplane`, `deploy/check-nginx.py`), миграции с нуля и повторно на пустой базе PostgreSQL
(`tests/test_migrations_postgres.py`), включая лечение оборванного индекса.

Не проверено (в песочнице нет Docker и живого сервера): сам прогон `deploy/update.sh` на вашей
конфигурации и откат образов. Поэтому первый шаг — резервная копия, и первый прогон лучше делать,
когда рядом есть возможность посмотреть логи: `docker compose logs --tail=80 backend`.
