# Хранилище файлов: что где лежит, как чистится и что бэкапить

Документ отвечает на один вопрос: **где физически находится каждый файл** и что с ним
происходит при замене, архивировании и удалении. Всё содержимое — в S3-совместимом
хранилище (REG.RU, MinIO, AWS S3 и т. п.). Локальный диск приложения используется
только как временный буфер и не хранит пользовательские файлы.

## 1. Ключи объектов

| Префикс | Что это | Кто создаёт | Удаляется вместе с |
|---|---|---|---|
| `modules/<slug>__<id>/_versions/<hex>.<ext>` | Оригинал файла материала (и каждая прошлая версия — отдельный объект) | `services/content.py` | файлом материала (навсегда — только из архива) |
| `modules/<slug>__<id>/_sources/<job>.zip` | Исходный ZIP импорта модуля (нужен для повторного импорта и разбора) | `routers/content.py`, `routers/admin.py` | модулем |
| `uploads/sources/<hex>/<имя>.zip` | ZIP, загруженный в админке до импорта | `routers/admin.py` | задачей импорта или вручную из «Хранилища» |
| `renditions/<asset>/<version>/<hex>.mp4<br>renditions/<asset>/<version>/<hex>.pdf` | Браузерная копия (MP4 или PDF) | медиа-воркер | файлом материала |
| `thumbs/<asset>/<version>/<hex>.jpg` | Превью 512 px для списков: кадр видео или уменьшенное фото | API (`services/thumbs.py`) | файлом материала |
| `sales/<section>/<путь>/<имя>` | Старое (legacy) хранилище файлов продаж; только чтение и «усыновление» в БД | существовало до миграции | не удаляется автоматически |
| `managed/sales/<section>/<hex>.<ext>` | Новые файлы продаж | `services/sales_library.py` | записью библиотеки продаж |

Важно: **имя файла никогда не является ключом**. Ключ — случайный hex, поэтому
переименование, перемещение по папкам, замена и удаление не трогают содержимое
хранилища и не могут перезаписать чужой файл.

## 2. Что происходит с файлом

- **Замена** — новый объект, старая версия остаётся в `_versions/` и доступна в истории.
- **Архив** — только флаг в базе. Объект и все производные остаются.
- **Удаление навсегда** — сначала запись помечается архивной, затем удаляются строки
  (`content_assets`, `asset_revisions`, `asset_renditions`, `asset_thumbs`,
  `sales_entries`) и **после коммита** — объекты в S3. Если S3 в этот момент недоступен,
  строки уже удалены, а объект остаётся «сиротой» до задачи очистки: файл не появится
  в интерфейсе, но и не сломает базу.
- **Замена версии** — превью и браузерная копия привязаны к версии источника
  (`source_version`), поэтому устаревшая копия никогда не будет показана вместо новой.

## 3. Временные данные приложения

| Путь | Назначение | Очистка |
|---|---|---|
| `/data/upload-staging/<upload_id>/` | куски большой загрузки (8 МиБ каждый) | TTL `UPLOAD_SESSION_TTL_HOURS` (24 ч) и сразу после успешной сборки |
| `/tmp/corelms_media_*` | рабочая папка медиа-воркера | удаляется по завершении задачи |
| `/data/upload-staging` на томе `backend_data` | переживает перезапуск контейнера | да, том постоянный |

Каталог сборки задаётся `UPLOAD_STAGING_DIR`. Он должен лежать на том же томе, что и
`backend_data`, иначе после пересоздания контейнера недособранные загрузки пропадут
(это безопасно — загрузка начнётся заново, — но лучше не терять).

## 4. Проверки, которые уже есть

- `GET /api/backend/admin/maintenance/thumbs/status` — сколько файлов с превью,
  сколько ждёт, сколько не удалось, суммарный размер превью.
- `POST /api/backend/admin/maintenance/thumbs/backfill` — поставить в очередь превью
  для старых файлов (кнопка в «Админ-центр → Настройки → Хранилище файлов»).
- `GET /api/backend/admin/maintenance/modules/storage-scan` — сверка модулей и объектов.
- `GET /api/backend/admin/storage/objects` — просмотр объектов бакета.
- `GET /api/backend/admin/settings/storage` + «Проверить хранилище» — доступность бакета.
- Очистка осиротевших объектов — задача `corelms_cleanup` (`services/storage_cleanup_jobs.py`),
  она использует полный набор «живых» ключей, включая `asset_thumbs`.

## 5. Права и ссылки

- Публичных ссылок на файлы нет: доступ идёт через API и проверяется по роли и модулю.
- Presigned-ссылки живут 15 минут по умолчанию (`S3_PRESIGN_DOWNLOAD_EXPIRES_SECONDS`)
  и используются только для скачивания/загрузки напрямую в S3.
- Отдача браузеру (`/assets/{id}/stream`) поддерживает `Range`, поэтому видео
  перематывается без скачивания целиком.
- Превью (`/assets/{id}/thumb`) кэшируется браузером на неделю (`private, max-age`),
  но требует авторизации: ссылка без куки ничего не отдаст.

## 6. Что бэкапить

1. **PostgreSQL** — все метаданные, права, историю, привязки файлов (`scripts/backup.sh`).
2. **S3-бакет** — сами файлы. Бэкап на уровне бакета: версионирование или синхронизация
   в другой бакет/провайдера.
3. **`backend_data`** — только для недособранных загрузок; восстанавливать не обязательно.
4. **`redis_data`** — сессии и очередь задач; восстанавливать не обязательно
   (люди просто войдут заново).

Порядок восстановления: сначала база, потом бакет. Если восстановить только базу,
файлы будут отдавать 404 с понятным сообщением; если только бакет — файлы просто
не будут видны в интерфейсе, пока не восстановится база.
